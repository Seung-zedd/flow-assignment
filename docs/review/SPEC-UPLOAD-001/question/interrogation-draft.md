## Category 1: Internal Contradiction

**Q1. 파일당 4MB · 요청당 5개 · 단일 `Content-Length` 게이트가 동시에 성립하지 않습니다.**

- `spec.md:119` — "시스템은 요청당 파일 5개, 파일당 4MB 상한과 확장자 부재를 서버에서 강제해야 한다. 크기 초과는 본문 스트림을 소비하기 전에 `FILE_TOO_LARGE`(413)로 거부해야 하고"
- `acceptance.md:77` — "`Content-Length`가 `MAX_UPLOAD_BYTES`(4MB)를 초과하는 요청이 도착하면"
- `plan.md:119` — "`Content-Length`로 4MB(`MAX_UPLOAD_BYTES`) 초과를 본문 파싱 전에 거부"

`Content-Length`는 요청 전체의 크기이지 파일별 크기가 아닙니다. 본문을 파싱하기 전에는 파일별 크기를 알 수 없으므로, "파일당 4MB"와 "본문 소비 전 거부"는 같은 게이트에서 함께 성립할 수 없습니다. 동시에 "요청당 5개"는 5개 파일이 합계 4MB 안에 들어와야만 실현되므로, 파일당 4MB라는 문구가 가리키는 상한은 실제로 도달할 수 없습니다.

4MB가 요청 전체의 예산인지, 파일 하나당의 상한인지에 대한 판단이 필요합니다. 후자라면 본문 소비 전 거부라는 순서 계약이 어느 지점으로 이동하는지도 함께 결정되어야 합니다.

**Q2. "거부에도 정확히 1행"과 "본문 소비 전 거부"가 `upload_attempt`의 NOT NULL 제약과 충돌합니다.**

- `spec.md:127` — "시스템은 업로드 성공과 거부 양쪽 모두에 대해 `upload_attempt` 테이블에 정확히 1행과 구조화 로그 1줄을 남겨야 하며"
- `spec.md:119` — "크기 초과는 본문 스트림을 소비하기 전에 `FILE_TOO_LARGE`(413)로 거부해야 하고"
- `plan.md:85-89` — `original_name varchar(255) NOT NULL`, `size_bytes integer NOT NULL`

본문을 소비하기 전에 거부하면 파일명과 파일별 크기를 알 수 없습니다. 그 상태에서는 `original_name`·`size_bytes`가 NOT NULL인 행을 만들 수 없으므로, "거부에도 1행"과 "본문 소비 전 거부"가 동시에 지켜질 수 없습니다. `TOO_MANY_FILES`(요청 단위 거부)도 같은 구조에 놓입니다 — 요청 단위 거부에는 대응되는 "파일"이 없습니다.

요청 단위 거부를 감사 기록에서 제외할지, 아니면 기록을 위해 스키마 제약이나 거부 시점을 바꿀지에 대한 판단이 필요합니다.

**Q3. "모든 업로드 AC는 엔드포인트 직접 호출"이라는 선언과 AC 본문의 화면 표시 단언이 충돌합니다.**

- `spec.md:49` — "G5 … AC-UPLOAD-008 ~ 015 (모두 엔드포인트 직접 호출로 수행 — 클라이언트를 거치지 않는 경로가 곧 우회 재현)"
- `acceptance.md:58` — "AC-UPLOAD-008 … 화면에 **걸린 세그먼트 `exe`가 명시된** 거부 사유가 표시된다."
- `acceptance.md:73` — "AC-UPLOAD-010 … 거부 사유에 '확장자가 없어 정책을 적용할 수 없음'이 드러난다."
- `spec.md:214` / `acceptance.md:149` — 컴포넌트 테스트 표면은 `FixedExtensionList.svelte` 하나(AC-016a 전용), `spec.md:203-205`는 브라우저 E2E를 배제

엔드포인트를 직접 호출하는 경로에서는 화면 표시를 관찰할 수 없고, 선언된 컴포넌트 테스트 표면(`FixedExtensionList` 1개)과 E2E 배제 아래에서는 이 화면 단언을 실행할 수 있는 테스트가 존재하지 않습니다. 같은 AC가 두 개의 서로 배타적인 검증 경로를 동시에 요구합니다.

화면 단언을 AC에서 분리할지, 컴포넌트 테스트 표면을 넓힐지, 수동 확인 항목으로 내릴지에 대한 판단이 필요합니다.

## Category 2: Ambiguous Subject/Condition

**Q4. REQ-UPLOAD-013의 "내용 판별을 계속 적용"이 두 가지로 읽힙니다.**

- `spec.md:122-123` — "차단 목록에 활성 항목이 하나도 없는 동안에도, 시스템은 크기 제한·개수 제한·확장자 부재 거부·내용 판별을 계속 적용해야 한다."
- `spec.md:107` — REQ-UPLOAD-009: 판별된 확장자가 "차단 목록에 있을 때" `SIGNATURE_BLOCKED`

읽기 A — "적용"은 판별 실행과 기록(`detected_mime`, `mismatch`)을 뜻한다. 이 경우 목록이 비어 있으면 내용 판별은 어떤 거부로도 이어지지 않으며, 앞의 세 항목(크기·개수·확장자 부재)과 달리 강제 효과가 없습니다.
읽기 B — "적용"은 앞의 세 항목과 같은 층위의 강제를 뜻한다. 이 경우 목록과 무관하게 작동하는 내용 기반 거부 기준이 별도로 존재해야 하는데, 그런 기준은 어느 REQ에도 없습니다.

AC-UPLOAD-010·011은 빈 목록 상태에서 `NO_EXTENSION`과 `FILE_TOO_LARGE`만 확인하고 내용 판별은 확인하지 않으므로, 인수 기준으로도 두 읽기가 갈리지 않습니다.

빈 정책 상태에서 내용 판별이 관찰 전용인지 강제 수단인지에 대한 판단이 필요합니다.

**Q5. 파일명에서 추출한 후보에 별칭 정규화가 적용되는지가 REQ마다 다르게 서술됩니다.**

- `spec.md:79` — REQ-UPLOAD-005: "별칭 표는 단일 원본이어야 하며 **업로드 판정 경로와 정책 저장 경로가 같은 표를 참조**해야 한다"
- `spec.md:98-99` — REQ-UPLOAD-007: 파일명은 "NFC 정규화·제어문자 제거·경로 구분자 제거·255바이트 절단한 뒤, … 소문자 확장자 후보로 추출" (별칭 언급 없음)
- `spec.md:103` — REQ-UPLOAD-008: "추출된 후보 중 하나라도 차단 목록에 있을 때" (별칭 언급 없음)
- `spec.md:107` — REQ-UPLOAD-009: 내용 판별 확장자는 "별칭 정규화 후" 대조

읽기 A — 파일명 후보도 대표형으로 접힌다. `jpg`를 차단하면 `photo.jpeg`도 거부됩니다.
읽기 B — 별칭 정규화는 내용 판별 경로(REQ-009)와 정책 입력 경로(REQ-005)에만 적용된다. `jpg`를 차단해도 `photo.jpeg`는 파일명 대조를 통과합니다.

`acceptance.md:139`의 엣지 케이스는 "커스텀에 `jpeg` 추가 → `jpg`로 저장·표시되고 `.jpg` 업로드가 차단됨"까지만 다루고 `.jpeg` 파일명의 거동은 다루지 않아, 인수 기준으로도 두 읽기가 갈리지 않습니다.

파일명 후보에 별칭 정규화가 적용되는지에 대한 판단이 필요합니다.

**Q6. `upload_attempt.original_name`이 정규화 전 값인지 정규화 후 값인지 불명확합니다.**

- `spec.md:115` — REQ-UPLOAD-011: "**원본 파일명**은 메타데이터로만 보관한다"
- `spec.md:98` — REQ-UPLOAD-007: 파일명을 "NFC 정규화·제어문자 제거·경로 구분자 제거·255바이트 절단"
- `plan.md:85` — `original_name varchar(255) NOT NULL` (바이트가 아닌 문자 단위 상한)

읽기 A — 클라이언트가 보낸 값 그대로를 보관한다. 감사 충실도는 높지만, 제어문자·경로 구분자가 그대로 들어가고 255바이트 절단이 적용되지 않아 `varchar(255)` 상한을 넘길 수 있습니다.
읽기 B — 정규화·절단을 거친 값을 보관한다. 저장은 안전해지지만 그 값은 더 이상 "원본"이 아닙니다.

감사 기록에 남길 값이 클라이언트가 보낸 그대로인지 정규화 후 값인지에 대한 판단이 필요합니다.

**Q7. `EXT_DUPLICATE` 판정의 비교 대상이 입력값인지 대표형인지 불명확합니다.**

- `spec.md:90` — "이미 저장된 커스텀 항목과 동일 | `EXT_DUPLICATE` | 409"
- `spec.md:79` — REQ-UPLOAD-005: 정규화(별칭 대표형 변환 포함) "한 뒤에만 저장·비교"
- `acceptance.md:24` — AC-UPLOAD-003: "화면에 '이미 추가된 확장자예요' 취지의 문구가 표시된다"

읽기 A — 대표형끼리 비교한다. 목록에 `jpg`가 있을 때 사용자가 `jpeg`를 입력하면 `EXT_DUPLICATE`가 반환되지만, 사용자가 입력한 문자열은 화면 목록 어디에도 보이지 않아 "이미 추가된 확장자예요"라는 문구와 화면이 어긋납니다.
읽기 B — 입력 문자열 기준으로 비교한다. 이 경우 `jpeg`는 중복이 아니어서 저장 단계로 넘어가고 `UNIQUE(extension)` 위반으로 처리 경로가 갈립니다.

별칭 충돌 시 사용자에게 어떤 사유와 문구를 보일지에 대한 판단이 필요합니다.

## Category 3: Implicit Assumption / Scope Creep

**Q8. `GET /api/uploads/recent`가 REQ·AC 없이 파일 목록에만 존재합니다.**

- `spec.md:163` — "`src/routes/api/uploads/recent/+server.ts` | 신규 | `GET` 최근 시도 20건"
- `plan.md:207` — "`GET` | `/api/uploads/recent` | 최근 업로드 시도 20건 (운영 관점 데모)"
- `spec.md:190-193` — §5.2 인증·사용자 개념을 만들지 않음(전역 단일 정책, 무인증 공개 배포)

이 엔드포인트를 규정하는 REQ가 없고 이를 검증하는 AC도 없습니다. 동시에 이 엔드포인트는 무인증 공개 배포 위에서 다른 사용자가 올린 원본 파일명·선언 MIME·탐지 MIME을 열람 가능하게 만듭니다. 구현 대상 목록에는 있으나 요구사항으로 확정된 적이 없습니다.

이 엔드포인트를 스코프에 포함할지, 포함한다면 노출 범위를 어디까지로 둘지에 대한 판단이 필요합니다.

**Q9. 다중 파일 요청에서 일부만 차단되는 경우의 응답 계약이 정의되지 않았습니다.**

- `plan.md:120` — "요청당 최대 5개(`MAX_FILES_PER_REQUEST`). **파일별 결과를 배열로 반환한다**"
- `spec.md:133` — REQ-UPLOAD-015: "모든 오류 응답은 `{ ok: false, error: { code, message, details } }` 형태를 가져야 하며"
- `acceptance.md:55-99` — 업로드 AC 전부가 파일 1개 · 단일 HTTP 상태(415/413)를 단언

5개 중 1개가 차단되고 4개가 정상인 요청에서 HTTP 상태가 무엇인지, 응답이 단일 error 봉투인지 파일별 결과 배열인지, 통과한 4개가 Blob에 저장되는지가 어느 REQ에도 없습니다. plan은 배열 반환을 전제하지만 REQ와 AC는 모두 단일 결과 형태입니다.

부분 성공 요청의 응답 계약과 저장 여부에 대한 판단이 필요합니다.

**Q10. REQ-UPLOAD-016이 어느 REQ도 규정하지 않은 클라이언트 측 확장자 검사를 전제합니다.**

- `spec.md:139` — "**클라이언트 측 확장자 검사는 UX 힌트이지 신뢰 경계가 아님**을 화면 문구에 명시해야 한다"
- `acceptance.md:120` — AC-016b: "'클라이언트 검사는 편의용이며 실제 차단은 서버가 수행한다'는 취지의 문구가 존재한다"
- `plan.md:352` — MX 태그 계획에 "클라이언트 검증 함수 | `@MX:WARN` | UX 힌트 전용"

클라이언트 측 확장자 검사를 만든다는 요구사항은 어디에도 없는데, 요구사항과 인수 기준은 그 기능의 존재를 설명하는 문구를 화면에 띄우도록 규정합니다. 기능 없이 문구만 있으면 화면이 존재하지 않는 동작을 설명하게 됩니다.

클라이언트 측 사전 검사를 실제로 만들지, 아니면 문구를 다르게 둘지에 대한 판단이 필요합니다.

**Q11. Blob 저장은 성공하고 DB 기록이 실패하는 경로가 "정확히 1행" 불변식의 전제 밖에 있습니다.**

- `spec.md:127` — REQ-UPLOAD-014: "성공과 거부 양쪽 모두에 대해 … 정확히 1행"
- `spec.md:50` — G6: "저장에 실패해도 화면 상태와 서버 상태가 어긋난 채 남지 않는다" → 판정은 AC-UPLOAD-016(정책 화면 한정)

REQ-014는 저장소 쓰기와 DB 쓰기가 어긋나지 않는다는 것을 전제하지만, 두 쓰기의 순서도 실패 시 보상 동작도 어느 REQ에도 없습니다. G6의 일관성 목표는 정책 화면(AC-016)에만 매여 있어 업로드 경로를 덮지 않습니다. Blob에 객체는 남고 감사 기록에는 아무 행도 없는 상태가 규정 밖에 놓입니다.

고아 객체를 감수할지, 순서·보상 동작을 요구사항으로 세울지에 대한 판단이 필요합니다.

## Category 4: Unverifiable-as-Written

**Q12. "…취지의 문구" 형태의 AC는 정확한 문자열이 어디에도 고정되어 있지 않아 이진 판정이 되지 않습니다.**

- `acceptance.md:29` — "안내 문구가 '고정 확장자는 위 체크박스에서 관리'를 가리킨다"
- `acceptance.md:73` — "거부 사유에 '확장자가 없어 정책을 적용할 수 없음'이 드러난다"

테스트는 특정 문자열을 단언할 수밖에 없는데, 어떤 문자열이 정답인지는 문서 어디에도 확정되어 있지 않습니다. `plan.md:181-186`의 "사용자 메시지 방향" 열도 문구가 아니라 방향만 제시합니다. 구현자가 고른 임의의 부분 문자열을 테스트가 그대로 되받는 구조라, 통과 여부가 요구사항이 아니라 구현 선택에 의해 결정됩니다.

사용자 문구를 확정해 검증 가능한 상수로 둘지, 이 항목들을 수동 확인으로 내릴지에 대한 판단이 필요합니다.

**Q13. 4MB 상한의 "서버 강제"가 클라이언트가 보낸 헤더 값에만 의존합니다.**

- `spec.md:119` — REQ-UPLOAD-012: "요청당 파일 5개, 파일당 4MB 상한과 확장자 부재를 **서버에서 강제**해야 한다"
- `spec.md:49` — G5: "모든 판정이 서버에서 이뤄지며 클라이언트 검증을 우회해도 정책이 뚫리지 않는다"
- `acceptance.md:77-79` — 판정 입력은 `Content-Length`, 단언은 "본문 스트림 리더가 한 번도 호출되지 않았음"

`Content-Length`는 클라이언트가 제시하는 값이고, 청크 전송에서는 아예 없을 수도 있습니다. 헤더가 없거나 실제 본문보다 작게 신고된 경우 시스템이 어떻게 판정하는지는 어느 REQ에도 없습니다. 결과적으로 "4MB 상한이 서버에서 강제된다"는 주장은 헤더를 신뢰한다는 전제 위에서만 성립하며, 그 전제를 반증하는 테스트를 구성할 수 없습니다.

헤더 부재·허위 신고 시의 판정 기준에 대한 판단이 필요합니다.

## Category 5: Silent Product Decision

> 비교 대상: 요구사항 원문 (founder가 선언한 제품 의도의 출처)

**Q14. 확장자가 없는 파일을 415로 거부하는 결정이 요구사항의 "정상 파일은 업로드 성공 처리"와 다른 방향입니다.**

- `spec.md:119` — "확장자 후보가 하나도 없으면 `NO_EXTENSION`(415)으로 거부해야 하며"
- `plan.md:129` — "블랙리스트 모델에서 확장자가 없으면 적용할 정책이 없다. '모르는 것은 통과'가 아니라 '모르는 것은 거부'를 택한다"

요구사항은 확장자 없는 파일을 "고려하고 근거를 남길 항목"으로 제시했을 뿐 거부를 요구하지 않았습니다. 이 결정은 `README`, `Dockerfile`, `LICENSE`처럼 확장자가 없는 일반 파일이 전부 거부된다는 뜻이고, 사용자가 처음 마주칠 동작을 바꿉니다.

확장자 없는 파일을 거부할지 통과시킬지에 대한 판단이 필요합니다.

**Q15. 사용자가 입력한 확장자가 다른 문자열로 저장·표시되는 동작이 요구사항의 화면 예시와 다릅니다.**

- `spec.md:79` — REQ-UPLOAD-005: 정규화 마지막 단계가 "별칭 대표형 변환"
- `plan.md:157-165` — 별칭 표: `jpeg`→`jpg`, `tiff`→`tif`, `htm`→`html`, `mpeg`→`mpg`, `yml`→`yaml`. "`jpeg`를 추가하면 `jpg`로 저장·표시된다"

대소문자 정규화(`SH`→`sh`, AC-UPLOAD-002)와 달리 별칭 접기는 사용자가 입력하지 않은 문자열을 목록에 표시합니다. `yml`을 추가한 사용자는 목록에서 `yaml`을 보게 되고, `mpeg`를 추가한 사용자는 `mpg`를 보게 됩니다. `yml`/`yaml`, `mpeg`/`mpg`는 plan에서 "방어적 등록"으로 표기되어 있어 대표형 선택 자체가 임의 선택이기도 합니다.

입력값을 그대로 표시할지 대표형으로 접어 표시할지, 접는다면 사용자에게 그 사실을 알릴지에 대한 판단이 필요합니다.

**Q16. "요청당 파일 5개"의 근거가 어디에도 없습니다.**

- `spec.md:119` — "요청당 파일 5개 … 개수 초과는 `TOO_MANY_FILES`(400)"
- `plan.md:120` — "요청당 최대 5개(`MAX_FILES_PER_REQUEST`)" — 근거 서술 없음
- 대조: 4MB는 "플랫폼 한도 4.5MB에서 역산", 200개·20자는 요구사항 명시값으로 각각 출처가 있음

요구사항이 제한값의 근거를 명시적으로 요구했는데, 세 상한 중 5개만 출처가 비어 있습니다. `plan.md:348`의 MX 태그 계획도 `MAX_CUSTOM_EXTENSIONS`·`MAX_EXTENSION_LENGTH`·`MAX_UPLOAD_BYTES`의 출처만 기록하고 `MAX_FILES_PER_REQUEST`는 빠져 있습니다.

5라는 값의 근거, 또는 다른 값을 쓸지에 대한 판단이 필요합니다.

**Q17. AI 활용 기록이 REQ·AC 어디에도 없습니다.**

- `spec.md:177` — "`PROMPT_LOG.md` | 기존 | **run 단계에서 읽기 전용** — 오케스트레이터가 관리. 완결성 판정은 `acceptance.md` Q11"
- `acceptance.md:159` — Q11은 품질 게이트(수동 확인)이며 대응하는 REQ·AC 없음
